# Go and Rust support: one gate, three stacks, 3000 shared test cases

Added on 2026-11-07. BankShield HumanGate now implements one shared gate
specification (docs/GATE_SPEC.md) in three stacks that must agree with
each other on every test case:

- Python reference implementation, in stacks/shared/gate_reference.py.
- Go implementation, in stacks/go (gate package plus an HTTP middleware
  example).
- Rust implementation, in stacks/rust (gate library plus a small example
  binary).

All three run against the same shared test vectors in
stacks/shared/test_vectors.json, generated by
stacks/shared/generate_vectors.py with a fixed seed. The scenario
templates define the expected decisions; the implementations are tested
against the templates, they do not define the answers.

## What the 3000 cases are

- 2500 attack and fraud cases across the existing 7 groups:
  Web Application 350, API 350, Mobile Application 300,
  Authentication And Session 350, AI Agent 400,
  Banking Fraud And Transaction 450,
  Infrastructure Supply Chain And Insider 300.
- 500 legitimate cases (full proof payments and transfers, payments to a
  new payee, high value payments, beneficiary and security changes,
  ordinary views and logins).
- Scenario families include payment to a new payee, beneficiary addition
  followed by a transfer, a stolen token used on the wrong device,
  replayed nonce, a signature reused for a different payee or a different
  amount, overlay or accessibility abuse during payment entry, session
  hijack before a sensitive action, systematic API probing in a window
  before a payment attempt, and high value and high rate bursts.
- Pass rules are strict: an attack case never receives ALLOW on a
  sensitive route (verified count: 0), and legitimate cases measure false
  positives (verified count: 0).

## Verified results (run locally on 2026-11-07)

Toolchains: Go 1.27.3, Rust 1.99.1 (rustc and cargo), Python 3.

Python reference and parity check:

```
python3 stacks/shared/gate_reference.py stacks/shared/test_vectors.json
cases=3000 allow=500 challenge=889 block=1611
attack_allow_on_sensitive=0
legit_false_positives=0
ALL VECTORS PASS
```

Go (module bankshield/stacks/go):

```
cd stacks/go && go test ./...
verified 3000 test vectors: ALLOW=500 CHALLENGE=889 BLOCK=1611
PASS (TestVectors plus 4 hard rule unit tests)
gofmt clean, go vet clean, go build clean
```

Rust (crate bankshield-gate):

```
cd stacks/rust && cargo test
verified 3000 cases: ALLOW=500 CHALLENGE=889 BLOCK=1611
test shared_vectors ... ok
```

Every stack produced the identical outcome split (500 ALLOW, 889
CHALLENGE, 1611 BLOCK), which is the cross stack parity claim: three
implementations, one specification, one answer per case.

Existing suites, rerun after this work landed, with no changes to their
code: BankGuard gateway tests passed, BankGuard finance leak scan passed,
HumanGate tests passed, and the HumanGate Blocker suite still blocks or
challenges 120 of 120 attacks with 0 allowed on a sensitive route.
CI (.github/workflows/ci.yml) now also runs the Python parity check, the
Go tests, and the Rust tests on every push and pull request.

## How to run each stack

- Python: python3 stacks/shared/gate_reference.py stacks/shared/test_vectors.json
- Go: cd stacks/go && go test ./... (set BSG_VECTORS to use a different
  vector file; by default the test loads stacks/shared/test_vectors.json)
- Rust: cd stacks/rust && cargo test (BSG_VECTORS works the same way)
- Regenerate the vectors: python3 stacks/shared/generate_vectors.py
  (deterministic, fixed seed 20261107; the generator refuses to write a
  file that fails its own cross checks)

## Limits, stated plainly

Demo only. Every signal in the vectors is synthetic and no real bank data
is used anywhere. The vectors prove gate logic and cross stack parity.
They do not prove that a real bank is invulnerable.

The Go middleware example and the Rust example are integration sketches
that show how to call the gate; they are not production services.
Production use still needs, at minimum: server side authority for every
money decision, real WebAuthn passkey verification, real device
attestation (Play Integrity, App Attest, or web device binding), a real
nonce and rate store such as Redis instead of in memory state, audit
logging and alerting, permission based penetration testing, code review,
and compliance review. Copying this repository alone does not make any
service certified or compliant.
