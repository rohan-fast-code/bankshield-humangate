# Multi language support: one gate, five stacks, 5600 shared test cases

Added on 2026-11-25. BankShield HumanGate now implements one shared gate
specification (docs/GATE_SPEC.md, version 2) in five stacks that must agree with
each other on every test case:

- Python reference implementation, in stacks/shared/gate_reference.py.
- Go implementation, in stacks/go (gate package plus an HTTP middleware
  example).
- Rust implementation, in stacks/rust (gate library plus a small example
  binary).
- Java implementation, in stacks/java (Maven project, gate library plus a
  small example; the maintainer's core language).
- TypeScript implementation, in stacks/typescript (npm project, gate
  library plus a small example).

All five run against the same shared test vectors in
stacks/shared/test_vectors.json, generated by
stacks/shared/generate_vectors.py with a fixed seed. The scenario
templates define the expected decisions; the implementations are tested
against the templates, they do not define the answers. This document
supersedes docs/GO_RUST_SUPPORT.md for current counts; that document
records the earlier 2026-11-07 round (three stacks, 3000 cases).

## What the 5600 cases are

The vectors grew from 3000 to 5000 cases, then to 5600 cases, on
2026-11-25. The first 3000 cases are byte identical to the 3000 case
file verified on 2026-11-07; 2000 new cases were appended (1600 attack
and fraud, 400 legitimate), and then 600 more cases for the spec v2
families (all attack and fraud):

- 4700 attack and fraud cases across the existing 7 groups:
  Web Application 600, API 600, Mobile Application 500,
  Authentication And Session 700, AI Agent 850,
  Banking Fraud And Transaction 900,
  Infrastructure Supply Chain And Insider 550.
- 900 legitimate cases (full proof payments and transfers, payments to a
  new payee, high value payments, beneficiary and security changes,
  ordinary views and logins).
- The original scenario families are still there: payment to a new
  payee, beneficiary addition followed by a transfer, a stolen token used
  on the wrong device, replayed nonce, a signature reused for a different
  payee or a different amount, overlay or accessibility abuse during
  payment entry, session hijack before a sensitive action, systematic API
  probing in a window before a payment attempt, and high value and high
  rate bursts.
- New scenario families added in this round: cross border payment to a
  new payee, QR payment to an untrusted merchant, SIM swap followed by a
  device change, device farm bursts, credential stuffing bursts before a
  payment, refund abuse, and mule account patterns.
- Spec v2 families added in this round, from the current threats in
  docs/THREAT_MODEL_2026.md: disbursement diversion to a mule account,
  approval tampering followed by a legitimate process payment, agent
  overreach beyond task authorization, indirect prompt injection
  triggering a payment, mule chain transfers, and record deletion after
  a transfer. These families use the six new spec v2 signals (ac, dd,
  ag, pi, mc, rd) defined in docs/GATE_SPEC.md.
- Pass rules are strict: an attack case never receives ALLOW on a
  sensitive route (verified count: 0), and legitimate cases measure false
  positives (verified count: 0).

One correction that applies to every document in this project: the
Wells Fargo incident of 16 November 2026 was not a hack. JPMorgan Chase
confirmed a software bug in its on-premise hardware systems, said there
is no evidence it was cyber related, and an FBI official cited in
reporting said there was no indication of malicious or external cyber
activity. Wells Fargo itself reported technical issues only. That outage
is never presented as an attack in this repository.

Every stack produced the identical outcome split (900 ALLOW, 1587
CHALLENGE, 3113 BLOCK), which is the cross stack parity claim: five
implementations, one specification, one answer per case.

Performance, measured on 2026-11-25 on the same machine: the decision
function is constant time per request in every stack, with median
latency 13 ns (Rust) to about 680 ns (Python) and peak memory under a
sustained run from 112 bytes traced (Python) to about 102 MB RSS
(TypeScript, which is the Node runtime). The full measured table, the
benchmark commands, and the design choices are in
docs/PERFORMANCE.md. The runtime gate never loads the shared test
vector file; the vectors are test data only, read solely by the test
files and the Python reference checker.

Existing suites, rerun after this work landed, with no changes to their
code: BankGuard gateway tests passed, BankGuard finance leak scan
passed, HumanGate tests passed, and the HumanGate Blocker suite still
blocks or challenges 120 of 120 attacks with 0 allowed on a sensitive
route.

## How to run each stack

- Python: python3 stacks/shared/gate_reference.py stacks/shared/test_vectors.json
- Go: cd stacks/go && go test ./... (set BSG_VECTORS to use a different
  vector file; by default the test loads stacks/shared/test_vectors.json)
- Rust: cd stacks/rust && cargo test (BSG_VECTORS works the same way)
- Java: cd stacks/java && mvn test (BSG_VECTORS works the same way;
  the test uses a small hand-written JSON parser because Java has no
  built-in JSON support and the project takes no dependencies)
- TypeScript: cd stacks/typescript && npm test (BSG_VECTORS works the
  same way); npm run typecheck runs tsc --noEmit
- Benchmarks, one per stack: python3 stacks/shared/bench_decide.py;
  cd stacks/go && go test -bench=. -benchtime=5s -benchmem ./...;
  cd stacks/rust && cargo run --release --bin bench;
  cd stacks/java && java -cp "target/test-classes:target/classes:$(cat /tmp/jmh-cp.txt)" org.openjdk.jmh.Main DecideBenchmark -wi 3 -i 3 -f 0 (after building the JMH classpath, see docs/PERFORMANCE.md);
  cd stacks/typescript && npm run bench
- Regenerate the vectors: python3 stacks/shared/generate_vectors.py
  (deterministic, fixed seed 20261107; the generator refuses to write a
  file that fails its own cross checks, and cases 1..3000 are preserved
  from the earlier file)

## Limits, stated plainly

Demo only. Every signal in the vectors is synthetic and no real bank data
is used anywhere. The vectors prove gate logic and cross stack parity.
They do not prove that a real bank is invulnerable.

The Go middleware example, the Rust example, the Java example, and the
TypeScript example are integration sketches that show how to call the
gate; they are not production services. Production use still needs, at
minimum: server side authority for every money decision, real WebAuthn
passkey verification, real device attestation (Play Integrity, App
Attest, or web device binding), a real nonce and rate store such as Redis
instead of in memory state, audit logging and alerting, permission based
penetration testing, code review, and compliance review. Copying this
repository alone does not make any service certified or compliant.
